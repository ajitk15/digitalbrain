06

Traditional RAG, NaviRAG or graph RAG?

Three ways to find evidence. A query can combine them.

Traditional / vector RAGNaviRAGGraph RAG
Picture it asFinding relevant passagesExploring a topic hierarchyFollowing typed relationships
Example routeQuestion → similar chunksPolicy → approvals → exceptionsRequirement → function → test
Good question“How are refunds authorized?”“Which exceptions appear throughout this long policy?”“Which code and tests implement R-17?”
Main strengthSemantic discovery, even with different wordingActive navigation to related detailExplainable dependencies and traceability
Main limitationSimilarity does not prove correctness or full coverageWrong branches, summary errors and extra model callsMissing / incorrect edges can mislead
Proposed placeChat baseline, with keyword searchEvaluate for long, structured specsTraceability core for Code Factory
Do we need a vector database?

We need a vector index if we use semantic search. It can live in a database extension such as pgvector; it need not be a separate database product. The graph and original evidence remain necessary for traceability.

NaviRAG here means knowledge navigation, not embodied navigation. These are proposed tradeoffs, not measured performance claims. Comparison, research sources and evaluation plan

07

Code Factory: evidence → approved fixes

Expected

Specification R-17

Above ₹10,000 → manager approval.

Observed · example

Code snapshot

Approval check runs only above ₹20,000.

Deviation

Approval gap

₹10,000 < amount ≤ ₹20,000 can skip required approval.

  1. Analyze pinned sourcesRead approved specs, repository commits and eligible tickets. A missing graph edge is an investigation lead, not proof of a bug.
  2. Present a reviewable planShow evidence, file changes, tests, unknowns, risk, tools, agent models and permitted fallbacks.
  3. Human approvalAuthorized approver accepts the bounded plan. Changed scope, baseline or unapproved model choice requires renewed review.
  4. Run selected specialist agentsImplementer patches isolated worktree; test agent checks boundaries; reviewer inspects results.
  5. Create PR & apply merge policyRepository checks and permissions control merge.
  6. Refresh & verify closureUpdate knowledge from the merged commit; recheck R-17; record the verified ticket outcome.
Tests proposed in the plan

₹10,000: no manager approval from R-17 alone. ₹10,001: required. ₹20,000: required.

Owner enables access → grants an application identity and scopes → developer authenticates → every call checks application and source permissions.

Endpoint controls

Use authenticated remote MCP with supported protocol/client versions, audience validation and per-request authorization. No token passthrough. Bound traversal and response sizes; isolate caches and audit records. Read-only knowledge tools never expose unrestricted database queries, graph writes or code execution.

Digital Brain

Digital Brain turns the documents, tickets, incidents and code a team already owns into evidence the business can stand behind — then puts that evidence to work in the two places it pays back fastest: software delivery and service operations.

00

Overview

Why we are building it

The problem

The knowledge that keeps delivery and operations moving is real, but it is scattered — a spec here, a Jira thread there, a postmortem nobody re-read, and the code itself. Finding it is slow, and it walks out of the door with the people who hold it.

Why general AI does not solve it

Off-the-shelf assistants answer from training data, so a confident wrong answer looks exactly like a right one. There is no way to check the working — which is why they stay out of anything that carries real risk.

What we are building instead

Digital Brain keeps our own material as immutable, digested sources and answers only from them — quotes attached, re-checked against the live source at the moment of answering. If it cannot be evidenced, it is not shown.

In the software lifecycle

  • Onboarding — a new engineer asks the system instead of interrupting a senior one, and gets the source, not a summary
  • Analysis — a ticket is checked against what we have actually written down, so gaps surface before work starts
  • Change — a bug ticket becomes a draft pull request with a stated rationale; engineers review a proposal instead of a blank page
  • Traceability — knowledge and a pinned code snapshot sit side by side, so "why is it like this" has an answer with a date on it

In service operations

  • Triage — "have we seen this before" is answered from our own incidents and runbooks, with quotes, in seconds
  • Escalation — the responder gets evidence rather than a guess, and can see exactly which document it came from
  • Safety — the platform reads; it never executes a runbook, updates a ticket or touches the live service
  • Learning — the postmortem is imported like any other document, so the next incident starts better informed

Both sides read the same approved evidence, inside one boundary: the application. A team's sources, knowledge, credentials and API keys are scoped to it and nothing crosses — which is what makes one platform safe to share across business units.

Organization, applications and roles

Neither admin role carries application access. A platform administrator and an organization administrator both get 404 — not 403 — on an application they hold no grant for, and creating an application does not grant one. Approval is a separate flag, not a fourth role: it can sit on any grant, and the approver can never be the person who wrote the plan.

02

System overview

The whole platform in seven steps. A team starts with whatever it has — documents, a repository, or both; neither is required. Everything that arrives is kept immutable, the knowledge is refreshed automatically at no cost, and a person decides when it becomes the version that answers. Both ways of working then read that same approved version, and what they produce comes back in as new evidence.

Steps 1–4 · building the evidence

  • Documents or a repository — neither one is required
  • Each becomes an immutable source; code stays separate
  • The worker rebuilds the graph whenever a digest changes
  • A person publishes a revision; nothing answers until then

Steps 5–7 · using it, closing the loop

  • Chat and Code Factory read that same published revision
  • A cited answer, or a draft pull request behind two gates
  • What returns: a postmortem, an RFC, a merged pull request
  • Dashed edges are carried by a person today — proposed to be automatic
03

Knowledge graph management

How the knowledge stays current without running up a bill. Keeping it in step with the sources is automatic and costs nothing; the paid AI step happens only when someone asks for it, so a routine refresh can never repeat a charge. And nothing new answers a question until a person approves it.

workflow · 3 lanes · automatic vs. human Open standalone ↗

Currency is automatic; publishing is not

  • The worker compares a fingerprint over every active source and rebuilds on any change
  • A structural rebuild is free and always saves a draft revision
  • Only a human promotes a draft, and publish refuses one whose evidence has moved
  • A failed generation is never retried on its own — a person asks again

Who reads it, and how

  • Chat, /graph/search/ and the MCP server all answer from the published revision
  • Neither machine surface calls a model, so no caller can spend the AI budget
  • A request may pin a version; every response states which one answered
  • No published revision is a 409 — never a quiet fallback to a draft
04

SDLC · bug fix

From a ticket to a reviewed draft pull request. The system works out what is being asked, what is missing and which files would change — then stops and shows its work. Approving that plan is one decision by a second person; writing to the repository is a separate decision with its own credential. Engineers stay the reviewers, never the bystanders.

workflow · ground → describe → write and deliver Open standalone ↗

The ticket is data, never instruction

  • Ticket text is evidence about a want, not a command to obey
  • A repository named in a ticket is confirmed by a person first
  • Each cited quote is re-checked against the live source
  • A failed phase halts the run and the record says why

Two gates, both owned by people

  • Approval needs a different user holding the approve permission
  • Approving a description does not authorise a repository write
  • Verification runs before anything is written; failure means nothing is written
  • Delivery opens a draft PR on its own digital-brain/* branch
05

SDLC · incident management

During an incident the platform gives the responder verified evidence — and touches nothing. No runbook is executed, no ticket is updated, no action is taken on the live service. The human stays in command. Afterwards the write-up is imported like any other document, so the next incident starts better informed than the last.

workflow · ground → answer with evidence → act and learn Open standalone ↗

An incident record is just a source

  • ServiceNow, Jira and GitHub imports are bounded and manual, not a mirror
  • Each record becomes an immutable source with a SHA-256 digest
  • A changed record archives the old revision instead of overwriting it

The platform never touches the service

  • No runbook is executed, no ticket is updated, no action is taken
  • REST and MCP callers get the same verified evidence and call no model
  • A code change goes back through the Code Factory gates, not around them

This is the flow as it stands. ServiceOps (section 06) proposes the next step: a triage brief built before anyone asks, from past incidents, runbooks and recent changes, with a confidence score computed from the evidence. Read the proposal →

06

ServiceOps · incident triage

in progress  The first read-only ServiceOps tab now shows imported incident context, similar resolved records and verified graph passages. The architecture below proposes the next stages: recent changes, up to three cited causes, and a confidence score the platform computes from evidence rather than asks the model for. The responder decides; confirmed outcomes, rather than clicks alone, calibrate the score.

What section 05 gives today

A responder can ask chat about an incident and get a cited answer. But they have to know what to ask, past incidents are just more text in the pile, and nothing says how much to trust the answer.

What triage actually needs

"Have we seen this before, what fixed it, what changed, and who owns it" — answered before anyone asks, ranked, with the reasons a senior engineer would give, and honest about when it does not know.

What ServiceOps adds

A structured incident memory, a model-free evidence pack that works even when the AI provider is down, a single bounded model call over that pack, and an evidence score that abstains instead of guessing. Calibration is added only after confirmed outcomes exist.

6.1

Triage architecture

Three stages, and the order is the design. Evidence first, deterministically without a model charge. Reasoning second, in one bounded call that may only cite what the evidence pack already holds. Trust last: citations re-verified, scores computed, and a person deciding.

Why the model cites by id. What leaves the platform is redacted: emails, phone numbers, card numbers and anything shaped like a secret are masked before the model sees them. If the model quoted redacted text, no quote would ever match the stored source. So it names a passage from the pack, and the platform cuts the quote from the stored source — the redaction protects privacy without weakening verification.

6.2

Confidence score

The same rule as citations, applied to certainty: what the model claims is not evidence. A model asked how sure it is will answer fluently and badly. The score is computed from things the platform can check, it is capped by what is missing, and it earns a percentage only once real outcomes show what its numbers mean.

A score means how well the evidence supports this hypothesis — not the chance that a mitigation will work. Each precedent's similarity is shown on its own row of the brief; it enters a hypothesis's score only through the precedents that support that hypothesis.

What each band does

BandWhat the responder seesWhat the platform must do
HighThe leading hypothesis and the precedents that match it closelyShow supporting and conflicting citations side by side; the next step is still a check a person runs, never an action
MediumSeveral ranked hypotheses and what separates themRecommend the one diagnostic observation that best tells them apart
LowA lead worth checking, with its gaps namedList the missing signals that would raise or sink it
InsufficientThe evidence found, and a plain statement that it is not enoughPropose no cause and show no percentage; ask for the missing signals or suggest escalation

Signals

SignalWhat it measuresHow it is computedWeight
M · matchHow closely the best supporting precedent resembles this oneExact fingerprint 1.0; same CI and error class 0.7; same service and term overlap scaled below that; decayed by age. A precedent that resolved some other way counts as counter-evidence, not match0.25
A · agreementWhether the precedents resolved the same wayShare of the top five precedents (match ≥ 0.5) whose close code or resolution agrees with the hypothesis0.20
V · citation coverageHow much of the hypothesis has intact source referencesClaims mapped to a current, exact pack passage ÷ claims made. The headline claim needs a valid citation or the hypothesis is dropped. This checks provenance; semantic support is measured separately by reviewed examples0.20
C · change correlationWhether a relevant change preceded the symptomA change on the same CI and before onset, with a relevant deployment or configuration diff, decayed with time since: exp(−Δt / 6h). Time proximity alone is not proof of cause0.15
R · reliabilityHow much the supporting sources can be trustedBy kind: a reviewed postmortem or approved runbook 1.0; a structured close code 0.8; close notes 0.6; a ticket's free-text body 0.40.10
D · diversityWhether independent kinds of evidence point the same wayDistinct kinds among incident, runbook, change and code, capped at three: min(n, 3) / 30.05
F · freshnessWhether the evidence is still about the system as it isPenalises a runbook older than the last change to its service, and precedents over a year old0.05

Score, then caps

raw = 0.25·M + 0.20·A + 0.20·V + 0.15·C + 0.10·R + 0.05·D + 0.05·F

# caps are applied after the sum, and the brief says which one fired
no verified citation            → Insufficient
one kind of evidence only        → at most Medium
a recent precedent disagrees     → at most Medium, both shown
no published graph               → runbook signal absent; says NO_GRAPH
model's own confidence           → ignored, never an input

From a score to a probability

  • 1Until an application has at least 200 independently confirmed outcomes, show only a provisional evidence-strength band — no percentage it has not earned
  • 2After that, a nightly isotonic fit maps the raw score to how often the hypothesis was confirmed for that application. Report service and severity slices only when each has enough labels; otherwise mark the slice insufficient
  • 3The brief can then read "High — 88% of 214 comparable triages were confirmed", with the sample size and calibration period beside it
  • 4Band edges are moved so High keeps ≥ 85% precision; a drop of ten points over 30 days raises an alert. Weights and edges are set by replay, never by hand-tuning on live incidents
  • 5Every run stores its components and calibration version, so any score can be recomputed exactly

A high score must be arguable. The brief shows each signal as a bar, names any cap that fired, and lists the counter-evidence beside the evidence — a precedent that resolved differently is shown, not hidden. A responder who can see why the score is high can also see when it should not be.

6.6

Rollout, decisions and risks

Five phases, each with an exit test measured on replay rather than asserted. The first two spend nothing on AI, so the value of the incident memory is proven before anyone pays for reasoning over it.

P0 · Foundations

Structured ServiceNow fields, bounded paginated history backfill, change import, fingerprints, IncidentProfile, an as-of replay harness and a baseline.

  • Exit: baseline measured on ≥ 500 resolved incidents

P1 · Evidence pack

The ServiceOps tab with precedents, storms, runbooks and changes. No model.

  • Exit: recall@5 ≥ 0.80, pack p95 ≤ 3 s

P2 · Hypotheses

Triage agent, verification, starting bands, abstention, verdicts, caching, receipts.

  • Exit: top-3 hit ≥ 0.60, High precision ≥ 0.85, zero unverified citations, and time to first useful clue improves on replay

P3 · Calibrated & automatic

Isotonic calibration, earned percentages, auto-triage on sync, drift alerts.

  • Exit: ECE ≤ 0.08 over 30 live days

P4 · Closing the loop

Knowledge gaps, Code Factory hand-off, outcome capture and postmortem prompts. The triage feature remains read-only.

  • Exit: a resolved incident traces from its first signal to a published learning; owners opt in per application

Decisions to make — with a recommendation

  • ?Embeddings for similarity? Not in v1: fingerprint, CI and terms stay reproducible. Revisit only if replay recall misses 0.80
  • ?Write back to the ticket? Deferred outside this read-only rollout. If requested later, design and approve a separate work-note-only gate and credential
  • ?Show percentages? Provisional evidence-strength bands until 200 independently confirmed outcomes; then calibrated percentages with sample size and period beside them
  • ?Require a published graph? Not for precedents, which read active sources; yes for runbooks, and the brief says so
  • ?Who owns the auto-triage budget? The application owner, per day, visible on AI cost reports
  • ?When does a resolution become a precedent? A resolved record imported from the ticket system counts at once, as chat's Sources mode already reads active sources. A postmortem, or a link to "the real cause", goes through normal graph review first
  • ?Ingest monitoring alerts? Not in v1: an inbound alert webhook is a new surface with its own authentication to design. Tickets carry the alert reference; revisit once the brief proves useful

Risks and how the design meets them

  • !Cold start — little history means more abstentions, which is the honest answer; P1 shows value anyway
  • !Poor close notes — "fixed" teaches nothing; a precedent with no resolution text scores low on agreement
  • !Automation bias — counter-evidence is always shown, and High-band precision is watched
  • !Alert storms — grouped by fingerprint, bounded by lane concurrency and budget
  • !Hostile incident text — data, never instruction; scope is closed over before the run

The read-only releases preserve the platform boundaries. Deny by default, scope closed over, citations verified live, secrets in files, usage receipted, no background identity and progressive enhancement. ServiceOps adds two rules: confidence is computed, never claimed, and a hypothesis is never evidence. Feedback helps review, while a confirmed system-of-record outcome or reviewed write-up supplies a calibration label or future precedent.

Security

These are invariants, not settings — properties a future change cannot quietly erode, because each one is pinned by an automated test that fails the build. Weakening any of them is a recorded decision with a written trade-off, which is exactly what an assessor will ask to see.

Deny by default

Application access is re-evaluated per request against current database state. Platform administration does not imply application access, and revoking a grant takes effect on the next request — including for API tokens.

The AI cannot widen its own reach

Agent tools are locked to one application and one user before a run starts. The model can narrow what it looks at; it has no way to ask for more. A prompt-injection attempt in a ticket or document therefore has nothing to escalate to.

Citations verified against live sources

Before anything is stored or rendered: source still active, digest unchanged, excerpt still present. What the model claims is not evidence.

Credentials never enter the database

One file per provider per application, readable only by the service account. Never an environment variable, never a database row, never written to an audit log, never sent back to a browser. A database backup therefore contains no usable secret — only who set it, when, and a digest.

The server cannot be turned into a probe

Exactly one place fetches a user-supplied URL. It refuses private, loopback and reserved addresses, then pins the connection to the address it validated so DNS cannot change the answer underneath it. http/https only, no redirects, 8 MB and 20 s caps, no credentials attached — the standard server-side request forgery path is closed.

Revoking access closes the API too

An API token resolves to a person and then runs the same checks their browser session runs. There is no separate token permission model to keep in sync, so withdrawing someone's access shuts their integrations off with no extra step. Token secrets are stored hashed and compared in constant time.

Document conversion has no network

Files are converted in a subprocess that cannot open a socket at all. A malicious document has nothing to call home to.

No AI spend goes unrecorded

A missing or unreadable token count is treated as an error, not a free request — because the provider will still bill for it. Every model turn produces its own receipt against its own provider request ID.

No shared AI account

Each application uses its own provider credential, and an AI run is started with a blanked environment so it cannot inherit another application's key or an operator's personal login. This is what makes per-team AI billing and attribution real rather than nominal. Production refuses the development shortcut outright.

Model output cannot script the page

What a model writes is always treated as text, never as markup, and it is escaped on the server before it reaches a browser — deliberately producing no clickable links. A model talked into emitting a malicious payload has no way to execute it in a user's session.

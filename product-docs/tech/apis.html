APIs, MCP and SCIM

Machine surfaces live under /api/. They take a bearer token only - never a session cookie - and run exactly the access checks a browser request runs. There is no second permission model.

Tokens

  • Any member issues their own on Settings → API access; a token can never do more than its person. It is shown once.
  • Format dbk_<prefix>_<secret>; stored as a SHA-256 digest and compared with hmac.compare_digest. The secret is hashed even when no row matches the prefix, so a missing token and a wrong one cost the same.
  • The application in the address is resolved after the token is checked, so an address that names nothing is answered exactly like an invalid token: 401, without saying which.
  • api_auth.authenticate binds row security to the token's application. Revoking the person's grant closes the token with no extra code.
  • Rate limit: 120 requests per token per 60 seconds - one Redis counter per token and window when Redis is configured (503 if Redis cannot count), in process otherwise.
curl -H "Authorization: Bearer dbk_…" \
  https://<host>/api/v1/applications/<application id>/graph/search/?q=page+size

Path (under /api/v1/applications/<id>/)WhatCalls a model?
graph/search/Search the published graph; each result with its source and exact quote, verified at request timeNo - spend=False: no question embedding, no rerank, whatever the application switched on
mcp/Model Context Protocol server (protocol 2025-06-18)No
chat/, chat/<message>/stream/Ask a question (modes search, ai, graph; up to 4,000 characters); JSON, or server-sent events through the browser's own streaming workerYes - gated on the chat_api feature
triage/, triage/<run>/Start a ServiceOps triage for an incident; read its brief with current verificationStarting one does
automations/catalog/, automations/invoke/, automations/runs/<run>/List allowed automations; queue a real run with an idempotency key; read its receiptNo (it launches an automation - owner only)

The Chat API answers through workbench.answer_question and the browser's streaming worker - no second answering path, and no way for a caller to choose a model or a credential. The conversation is looked up by the token's own user. chat_api starts ticked on a new application (a deliberate convenience trade), but migration 0036 wrote it disabled for every application that existed before it, and the endpoint is unreachable without a token.

Browser routes worth knowing

Browser pages live under /applications/<uuid>/… (knowledge, chat, plans, runs, serviceops, settings) and /platform/… (administration). They take cookies only. Popups are plain pages: static/modal.js fetches the link and lifts its <main>, so every popup target also works as a full page with JavaScript off.

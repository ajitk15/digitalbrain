Answering and citations

How a question finds candidates, how they are ranked, how every citation is verified, and how the model is kept to evidence. One ranking (ranking.py) and one verification serve every path - chat, Code Factory, triage, the API and the benchmark.

Three answering paths

ModeCandidatesModel
Source excerpts (search)lexical_citations: keyword retrieval over active, answerable sources or their passagesNone - the answer is the readable evidence
AI answer (ai)The same keyword retrievalPurpose chat. On Claude and OpenAI it is an agentic run whose only tools are search_knowledge and fetch_source, bound before the run to one application and one user
Graph answer (graph)graph_citations on the latest published (or pinned) versionPurpose graph_retrieval; keyword retrieval is not run first (with reranking on it was a paid call for nothing)

The mode belongs to the conversation; ChatMessage.mode records what produced each answer. Every chat control is a plain POST form that reaches the synchronous path in workbench.answer_question with JavaScript off; static/chat.js only intercepts it to stream.

Finding candidates

  • Full text on PostgreSQL. A stored generated search_vector column with a GIN index on sources and passages (migration 0088). The earlier expression indexes made ts_rank re-tokenize every matching row on every question: 51 ms a keyword answer, 10 ms after.
  • Passages or sources (retrieval_candidates, default auto): passages are used only while every active source has current ones, because a source with none current would be missed rather than ranked lower.
  • Graph rows or memory (graph_candidates, default rows): every edge holding a question term is a candidate, ranked with the whole version's statistics. The scorecard holds rows and memory to identical citations on every benchmark question; rows were chosen because they do not grow with the graph (21 ms vs a warm 10 ms on CarePath).
  • References are one term. "C-09", "BR-05" and "NFR-06" are indexed whole beside the words and kept beyond the 20-word question cap - that alone took the graph benchmark to 16/16 at the time.

Ranking

  1. Coverage - texts holding more of the question's terms first.
  2. BM25 - then term weighting.
  3. Spread - each source's best citation before any source's second.

Measured against an earlier commit on CarePath: graph answers 11/16 → 15/16 found (MRR 0.53 → 0.69); keyword 8/16 → 14/16 (MRR 0.26 → 0.67); no question worse on either path. Ranking references ahead of words was tried and measured worse (evidence recall 76% → 60%), so it was not kept.

Why Every ranking change needs a before/after benchmark run. The scorecard's baseline today: graph 15/16 found, MRR 0.701; keyword 14/16, MRR 0.674; graph answer 8 ms and keyword 4.8 ms median.

The two-hop walk and followed references

  • graph_ai.walk goes breadth-first from the best AI relationships along other AI relationships, at most 2 hops, stopping at hubs (fan-out 25), adding at most 6 finds - after every direct match, each labelled "Reached by:". Structural edges are never walked: a value node such as "Status: Done" joins hundreds of records.
  • For Code Factory only, graph_ai.referenced adds up to 4 passages naming the most of the ticket's references, after the eight direct matches. Planted-bug evidence recall is measured by the scorecard (baseline 96%).

Embeddings

Embeddings choose starting points, never citations. A vector's nearest relationships or passages are fused with the BM25 order; every one is then verified exactly as a word match is. Vectors are content-addressed per application, so nothing is embedded twice and one application never uses another's. A failed question embedding answers by words and logs embedding_unavailable.

Verification

Before a citation is stored or rendered, it must still be active, have an unchanged digest, and its excerpt must still appear in the source. Walked and referenced citations are verified like any other. A passage found by meaning is re-read and re-hashed against the text that was embedded. Then:

  • Restricted sources are excluded on every path by KnowledgeEntry.objects.answerable().
  • Source-system permissions (Jira, when the connector enforces them) filter by asker and fail closed.
  • Reranking sees verified citations and returns their numbers; anything else is dropped, and any failure keeps the original order. Measure it with manage.py benchmark --rerank --as <user>, the one benchmark run that spends.

Rendering

Streamed text is inserted with textContent. A finished message is replaced by a fragment the server rendered with the chat_text filter, which escapes first and deliberately produces no links. There is one implementation, on the server; it is not reimplemented in JavaScript.

How AI extraction stays honest

Closed ontology

8 types, 12 relations, each relation with allowed types at each end and phrasings it absorbs. The prompt is written from the registry; the validator enforces it.

Exact quotes

A proposal whose quote is not in the source the model was reading is refused - including one naming another source's id.

Careful merges

Entities merge only on the same type and the same words (stem- or long-typo-equal, numbers exact). Each edge keeps its own source, digest and quote.

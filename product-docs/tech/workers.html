Workers, lanes and jobs

Background work runs in nine lanes (document_worker.LANES) so that a slow kind of work never waits in front of a fast one. Lanes run inside the web process by default, or in worker processes of their own.

The lanes

LaneTickWhy its own lane
intake1 sSomeone is waiting for their upload. Takes turns (document_worker.fairly): the oldest document from an application with nothing converting, else the oldest, so one large import cannot hold everyone's single upload.
graph2 sRebuilds and AI runs are long; they must not sit in front of an upload.
code-graph2 sClones and indexing are slow and run git.
factory2 sA Code Factory run makes several provider calls in sequence. Claims only prepare_queued.
serviceops1 sSomebody watches a triage's steps tick; it must not wait behind Code Factory.
serviceops-tests3 sThe test workbench's fixed suites.
automations2 sReal automation runs, launched once each.
connectors10 sAn import waits on somebody else's instance for tens of seconds; the shortest schedule an owner can choose is fifteen minutes.
maintenance30 sCheap sweeps where one holder is enough.

Jobs: asked for, not scanned for

The graph lane used to compute every application's fingerprint every two seconds, and the connector lane read every connector every ten - a cost that grew with applications, not with work. Now (jobs.py, models.Job):

  • A change writes a Job in its own transaction. That is the outbox: a rolled-back change takes its job with it, and there is no event table to drain. triggers.py asks for graph_refresh on anything in the fingerprint - a source saved or deleted, a queryset update on a graph field (querysets send no signal, so the queryset reports itself), graph settings, the Knowledge switch.
  • One waiting row per key (a partial unique index). A burst folds into one job, earliest due wins; graph_refresh waits five seconds so it can. Folding is an UPDATE, never a read, so a request racing a claim gets its own row.
  • Claims are SELECT … FOR UPDATE SKIP LOCKED on PostgreSQL, a conditional update on SQLite. An application holds at most TENANT_CAP (2) running jobs per lane. A running key is never started twice, so a change made mid-rebuild is rebuilt after it.
  • Leases (2 minutes, renewed by a thread) bring back a dead worker's job: maintenance puts it back, or marks it dead past max_attempts. A failed rebuild or import is one attempt - the queue never repeats a paid call or half an import; Later means "not yet" and costs no attempt.
  • Job.application_id is deliberately not a foreign key: deleting an application deletes its sources, each asks for a refresh, and a key to the row being deleted would fail the delete.
  • Reconcile (graphs.reconcile_if_due, every 600 s and at lane start) enqueues every candidate application for changes that came without a trigger - a bulk feature update, an organization reactivated, a restore.

Shared lanes and the one keeper

Every lane but maintenance is in SHARED_LANES: each step claims its own row first - a document by a conditional update, a job by a row lock, a run, triage, review or index by a guarded status change on its job token, a poll by moving its turn on. Work found by its age is kept fresh while it runs (keepalive.KeepAlive), so another process reads a stopped worker, never a slow one, and a paid review is never paid for twice. test_shared_lanes stages each race.

Maintenance is held by one process (LaneKeeper): a PostgreSQL session advisory lock on a connection of its own, so close_old_connections between steps never drops it, with a second holder standing by.

Two consequences. SQLite has no advisory locks, so every keeper "holds" there - never run run_worker beside a serve.py that runs its own lanes on the same SQLite file. And a session lock does not survive a transaction-mode connection pooler, so a worker connects to PostgreSQL directly.

Running them

HowCommand
Everything in one process (default, and local development)scripts/serve.py
Web onlyscripts/serve.py --no-worker (DIGITAL_BRAIN_ROLE=web)
Some lanes in a workermanage.py run_worker --lanes graph,connectors --concurrency factory=2 (DIGITAL_BRAIN_ROLE=worker, DIGITAL_BRAIN_LANES, DIGITAL_BRAIN_CONCURRENCY)

A test holds the scale overlay's two lane lists to LANES with no lane in both. A stop (SIGTERM) is honoured between steps, never inside one: a conversion or paid call that started is finished and recorded (stop_grace_period: 70s).

Health

Each holder writes a LaneHeartbeat. manage.py queue_status [--json] [--check] [--lanes …] reports each lane's waiting work, oldest age, heartbeat and dead jobs - counts and ages, never a record. Compose health checks name only the container's own lanes. The maintenance lane logs the same figures every five minutes as queue_status events.

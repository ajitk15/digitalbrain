Technical

Observability and service levels

Logs always, traces and metrics when an [otel] table names a collector, and service levels kept two ways: counted from the platform's own records, or ruled on metrics in Prometheus. What a span or metric may carry is a closed registry, so nothing a person or model wrote can leak into telemetry.

Traces: ids and timings only

Off by default (telemetry.py). Three things become spans:

  • A request - TelemetryMiddleware, first in the stack: method, the route's pattern (never the path), status, request id, application id.
  • A lane step that did work - with the job kind; idle steps are dropped.
  • A paid call - from the first try for a slot to its release: purpose, provider, model, wait, outcome, and an ai.receipt event per receipt (provider request id and token counts).

What a span may say is telemetry.ATTRIBUTES; anything else is dropped, so a prompt, answer, source text, name, URL or query cannot reach a collector by accident. Exceptions are recorded by class name, never message. No context is read from incoming headers or sent with outgoing calls; the global tracer provider is never set. One attempt per batch, one warning per five minutes when the collector is down, and the queue drops rather than grows. With no table the SDK is never imported.

Metrics

Same table and exporter (metrics.py; metrics = false turns them off alone; push every metric_interval_seconds, default 60). Rates, errors and durations of requests (streams marked streamed), lane steps, admission waits, admitted calls, answers by mode and outcome, receipt tokens and spend; gauges for each lane's waiting work, oldest age, dead jobs and heartbeat age, calls in flight, answers streaming.

  • metrics.INSTRUMENTS is a subset of the trace registry with two more rules: nothing new on every call is a label, and only spend carries an application id.
  • Database-reading gauges are read by the maintenance lane and held, so one process reports them.
  • Each process reports as its own random service.instance.id: without it, a web and a worker exported identical series and the collector kept the last - two processes recording 100 tokens each read as 100.
  • Prometheus names an attribute by its dotted name: lane arrives as digitalbrain_lane. Rules once selected lane=, which no series carries, so two alerts could never fire; now slo.label writes every label from the registry, test_slo checks each selector, and CI runs promtool check rules and promtool test rules.

Service levels

slo.py is a registry; manage.py slo [--check] [--json] [--rules]. Window 28 days; fewer than 20 events is reported, never failed.

Answers end with an answer, not a failure (a Stop is neither)99%Records

The metrics objectives are generated as multi-window burn-rate rules into deploy/slo-rules.yml. test_slo fails when the file and the registry differ - regenerate it, never edit it.

Without any collector

python manage.py queue_status --check
python manage.py slo --check

Logs are structured; a log line inside a span carries its trace_id. Every response carries X-Request-ID. The Administration → Operations page shows lanes and service levels in the browser, and the Overview lists stale lanes, dead jobs and objectives below target.

Health endpoints

/health/live and /health/ready. The container health check (deploy/healthcheck.py) sends a host name the application allows - otherwise Django answers 400 and the container never reports healthy while serving perfectly.

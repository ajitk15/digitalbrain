Tenancy and row security

An application is the tenant. Three layers keep one application's data from another: the code's own scoping, PostgreSQL row-level security underneath it, and a database role that can only touch rows.

Layer 1: the code decides access

  • Deny by default. Application access is re-checked on every request and every tool call. No grant → Http404 from policy.application_for, so the platform never confirms an application exists. Platform administration does not imply application access.
  • Live only when all four levels are on (policy.LIVE): organization, portfolio, product and application each have active. Read by applications_for, the gateway, connector scheduling and the graph lane, so turning a parent back on restores exactly what was on.
  • Scope is closed over, never model-supplied. Agent tools (agent_runtime/tools.py) are bound to one application and one user before a run. Model arguments may only narrow an already-scoped queryset; a foreign id reads as "not found", never raises and never leaks.
  • API tokens are users. api_auth.authenticate returns (user, application) and the same access() checks run. There is no token role and no token permission table, so revoking a grant closes the token with no extra code.
  • Background work runs as a person. A scheduled import runs as the connector's creator; automatic AI as whoever switched it on (or the first owner still able to open it). Each re-checks that grant, so revoking it stops the schedule with no code that knows about schedules.

Layer 2: row security

Migration 0091 gives every table with a required application a PostgreSQL policy, FORCEd (so it binds the table owner too), reading the session setting digitalbrain.tenant. Bound, a connection reads and writes only that application's rows; unbound, it sees everything.

tenancy.UNSCOPED names the four tables a request reads across applications - grants, features, logos, gateway admissions - and why. test_tenancy fails when a new model with a required application is in neither the policy list nor that set, so a new table makes its choice in its own migration. New tables after 0091 secure themselves through 0091's secure.

Row security defends against a missing filter, never against SQL injection, and it does not replace the code's checks - those still decide access. On SQLite there is none: the code is the only layer.

Layer 3: a role that can only touch rows

The role PostgreSQL's image creates is a superuser: it can read the server's files, run COPY … TO PROGRAM, drop anything, and is never held to row security. The platform used to run as it. Now:

  1. The migrate step connects as the owner ([database] user) with runtime_user naming the role to make.
  2. apply_migrations (database_roles.py), under its lock, creates or corrects digital_brain_runtime: LOGIN and nothing else, SELECT/INSERT/UPDATE/DELETE on every table, default privileges for tables later migrations add. Every run states it all again, so a privilege added by hand is undone.
  3. Everything else - web, worker, manage.py through docker exec - reads the configuration that connects as the runtime role (password_secret = "database_runtime_password").

The entrypoint renders both configurations. DIGITAL_BRAIN_DATABASE_RUNTIME_ROLE=0 connects as the owner again; an operator's mounted file is used for both. Runtime code never needs DDL - which is also why making audit partitions runs as the owner, in apply_migrations and manage.py partitions.

Disable and delete

  • Disabling is reversible. It fails work still queued under it (hierarchy.STOPPED) - which has cost nothing. A step already running finishes and its next paid call is refused. A schedule just waits.
  • Deleting is not. Offered only for a level already disabled, with the name typed exactly, by a platform administrator (everyone else gets 404), and refused while anything under it is in flight - checked under the same lock on application rows that gateway.try_admit takes. Content is removed deepest first; each level's row stays as a tombstone; audit events and receipts are never deleted with what they describe. Files go after the commit.

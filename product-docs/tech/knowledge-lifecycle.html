Knowledge lifecycle

Generate → draft → check → publish → use → learn. How an uploaded file becomes a published, verifiable graph, what each step guarantees, and what it costs.

1. Intake: from file to verified text

  • Upload, folder or link. A link import (link_sources.py) records a pending Document; the worker downloads it through fetching.py. Conversion never learns URLs exist.
  • Scan. Every original is scanned before conversion; anything not clearly clean is refused. With no scanner configured in production, documents are refused rather than stored unscanned.
  • Convert. scripts/extract_text.py runs as a subprocess whose socket.connect raises. OCR (when ocr = true) reads text-less PDF pages and images, at most MAX_OCR_PAGES (50) - over it the document fails rather than half-reads - and heads each page with its confidence.
  • Original kept or removed. With keep_original_documents = false the original is deleted on commit of a successful conversion; name, size, SHA-256 and the page report remain. A failed conversion always keeps its file.
  • Store. workbench.add_knowledge masks (if on), computes the digest of the stored text, writes the entry and its passages (KnowledgeChunk, 1,400-character windows every 1,200) in one transaction.
  • Judge. Source check (six checks, Ready = 80 and none missing), document type from content (a closed registry, no model), content check for that type, personal-data scan. All advice: nothing here ever leaves a source out of a graph.

2. Build: a draft version

A change to anything in the fingerprint writes a graph_refresh job in the same transaction. The graph lane builds:

  1. Structure, per source. Each source's fragment is built from that source alone and cached per process by entry, title and digest, so a rebuild after one change reads one source (1.9 ms warm on CarePath). Fragments merge in source order to exactly what a single pass produced. Every answerable source is taken - there is no cap on the library.
  2. AI enrichment - on by default (graphs.automatic_ai), refused with a reason on the version when graph generation is off, no owner can be charged, the credential is missing or the budget is spent. Long sources are read in windows (24,000 characters, at most 8). Each answer is cached under the digest of exactly what the model read before the next call starts, so nothing paid for is lost and nothing unchanged is paid for again. A reply that cannot be read costs its source, never the run.
  3. Judging proposals. The quote must be found exactly; the relationship must fit the ontology's types at each end; the subject may be the source itself (a ticket never repeats its own key). Refused and outside-ontology counts are kept on the version.
  4. Save. A GraphRevision as a draft, recorded as GraphElement rows: an element unchanged since the last version stays open, so only what changed is written.
Why A rebuild never repeats a paid call: a requested run is carried on KnowledgeGraph.requested_* and cleared once consumed, and a background rebuild carries cached answers forward with no model call. The scorecard holds "model calls re-running unchanged sources" at 0 and "after one source changes" at 1.

3. Check: benchmark and release check

Benchmark (free)

After each save, the owner's benchmark questions are scored through the same ranking and verification an answer uses: found, top-3, rank (MRR). It is scored again on the version with its AI removed, so Quality shows what AI added. Shape figures - cross-document links, largest connected piece, orphans, quoted relationships - are taken both ways.

Release check (rules, no model)

Hard - refuse whatever the reason: a source changed or retired since the build, a quote that no longer verifies, a source since restricted. Soft - compared with the published version, never an ideal: fewer questions found or lower MRR, AI that took answers away, a source dropped, more documents below Ready, more proposals refused. A soft failure publishes only with a typed reason, kept in the audit event.

4. Publish

  • Every path that publishes goes through release.publish, which checks again: the Versions popup, the old form, graphs.publish_revision, the demo script.
  • Automatic publishing is off by default and only an owner switches it on. The newest version then publishes itself as that owner only when every check, hard and soft, passed against the version that answers now, and it was benchmarked. The first version is always a person's. If the owner is demoted, removed or deactivated, it stops and says so.
  • graph_snapshot resolves to the latest published revision, never a draft. No published revision is an error, not a fallback.

5. Use

Graph answers, Code Factory evidence, ServiceOps runbook passages, REST graph search and MCP read the published version, prepared once per process (an LRU of 8). Safety comes from per-edge verification at read time, not from re-checking the whole graph: active source, matching digest, exact quote. Restricting a source therefore takes it out of already-published versions at once. How answers are ranked and verified.

6. Learn

learning.py collects candidates by rules from four records already kept - a delivered Code Factory run with every check passing, a confirmed triage verdict, an answer with no citation, an answer marked wrong. Nothing is knowledge until an owner or contributor accepts it. Accepted sources go through add_knowledge under learned://, which is excluded from requirement evidence so the platform never cites its own output as proof of itself.

How the cycle is shown

lifecycle.py works out Set up → Feed → Build → Check → Publish → Use from records already kept, with no model, and draws it on Onboarding and as a status strip on every Knowledge page (four queries whatever the library's size). Each stage links to the screen that acts; nothing in it writes.

The exception: the operations graph

ServiceOps' graph of incidents, changes, knowledge articles and automations is live, not publish-gated. It is rebuilt by rules whenever the fingerprint over incident and change ids and digests (plus the published knowledge revision and the day) moves, and every edge is re-verified against its records when read. Nothing a model says is written to it. The only edge a person makes is confirmed - a verdict's actual cause.

Deployment

Local development

A development machine can run the platform two ways: with the same services production uses, in Docker, or on its own with a SQLite file. The first is the normal way to work, because it is the only one where row security, the runtime role, Redis streaming and virus scanning behave exactly as deployed.

Why development runs production's services. A SQLite-only machine hides whole classes of bugs: PostgreSQL alone has the advisory locks the lanes use, SKIP LOCKED job claims, full-text indexes and row security. Two real defects were caught only there - a select_for_update beside an outer join, and a test that lost its connection - so CI runs on PostgreSQL too, and development does by default.

With Docker (the normal way)

  1. First run. Install Docker Desktop and Git, clone the repository, double-click start-all.cmd. With no .venv it treats the run as -Install: installs uv and builds the environment with uv sync --frozen from uv.lock (a pip path exists only for machines that cannot reach astral.sh, and resolves fresh), prompts for an administrator (password read hidden) and asks once for an AI provider credential.
  2. Every start. start-all.cmd again. It keeps the environment up to date but never downloads a toolchain, so an ordinary start stays predictable. Stop with stop-all.cmd.
  3. Options. -Port 8010; -ConfigureAI to ask the provider question again; -Demo to build the CarePath demonstration before the server starts (safe to repeat; it reports what exists).

Two configuration files, on purpose

scripts/init_local.py --services points config/local.toml at the Docker services once, and writes config/local.runtime.toml on every start. local.toml is the owner's - migrations, manage.py, the five gates. The server is started with the runtime file, which connects as digital_brain_runtime: a role that can read and write rows and nothing else. That is the same split a deployment's entrypoint renders.

ThingWhere it lives locally

Addresses, never localhost. Windows tries IPv6 ::1 first, which Docker does not publish, and every connection waited ten seconds for it. The configuration names 127.0.0.1.
ClamAV on a first start can keep serving its bundled signatures after freshclam replaced them; the platform then refuses every scan as stale - correctly. Restart the clamd service to load the new ones.

Without Docker

The platform runs with no services at all when its configuration has no [database] and no [redis] table:

Database

SQLite at .runtime/local.sqlite3, with immediate transactions. No row security: the code's own scoping is the only layer.

Server

waitress (the default without Redis). Answers stream from process memory; a dropped connection does not resume.

Scanning

Uploads need a scanner: clamscan on the machine, named by scanner, or conversion fails closed.

start-all skips the Docker services whenever DIGITAL_BRAIN_CONFIG is already set, so pointing it at a development configuration with no [database] table gives this shape. Whether a given version of the script also falls back on its own when Docker is not running, the result is the same: one process, SQLite, waitress, lanes in-process.

Never run manage.py run_worker beside a serve.py that runs its own lanes on the same SQLite file. SQLite has no advisory locks, so every lane keeper believes it holds maintenance.

On Linux or macOS

The start scripts are PowerShell. On another system, the same steps by hand:

uv sync --frozen                          # exact versions from uv.lock
docker compose -f docker-compose.dev.yaml -p digitalbrain-dev up -d --wait postgres redis
docker compose -f docker-compose.dev.yaml -p digitalbrain-dev up -d clamd
.venv/bin/python scripts/init_local.py --services
.venv/bin/python manage.py apply_migrations
.venv/bin/python manage.py collectstatic --noinput
DIGITAL_BRAIN_CONFIG=config/local.runtime.toml .venv/bin/python scripts/serve.py --instance dev

Skip the two docker compose lines and --services for the SQLite shape.

After you change things

  • Anything under static/: run manage.py collectstatic and restart the server. Templates resolve hashed names through the manifest, which the running process caches at boot.
  • Before calling it done: the five gates. manage.py test follows local.toml, so the suite runs on the local PostgreSQL too; the test runner blanks Redis, the scanner, telemetry, the bucket and the shared connector folder.
  • Telemetry locally: docker compose -f deploy/observability/compose.local.yaml -p digitalbrain-observe up -d, then an [otel] table with endpoint = "http://localhost:4318". Prometheus is on port 9090, bound to this machine only.
  • Before a restart, check whether a Code Factory run is in flight: restarting the server can stop it part way.

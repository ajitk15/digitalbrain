Deployment

AWS, Azure and Google Cloud

The platform needs five things from any cloud: containers for its four roles, PostgreSQL 16, a TLS Redis, somewhere for uploaded originals, and secrets delivered as files. This page maps each onto the three large clouds and says plainly what each mapping requires - including the parts the repository does not set up for you.

What has been run. The repository ships and runs Docker Compose on one server, with originals in an AWS S3 bucket. The managed-service mappings below follow from what the code requires (TLS rules, roles, locks, file permissions); they have not been run end to end on each cloud. Rehearse a deploy and a restore before relying on one.

What each piece must do

PostgreSQL

  • TLS is verify-full in production, always. Mount the provider's CA bundle and name it in sslrootcert; host must be a name on the server's certificate (the instance's DNS name, not an IP).
  • The owner must be able to create a role. apply_migrations creates or corrects digital_brain_runtime with LOGIN only (no superuser, CREATEDB, CREATEROLE, REPLICATION or BYPASSRLS), so the owner needs CREATEROLE. A managed service's administrator user normally has it; the platform never needs a true superuser.
  • Session advisory locks. Migrations, the maintenance lane's keeper and the gateway's per-provider admission hold PostgreSQL advisory locks. Connect directly, or through a pooler in session mode - never transaction mode, where a session lock does not survive.
  • Timeouts are the platform's. Each connection sets statement_timeout=10s and lock_timeout=5s; apply_migrations lifts the first for its own session.
  • Partitions are DDL. The monthly audit partitions are made by the owner - in every apply_migrations, and by manage.py partitions on a schedule (monthly is enough). The runtime role cannot.
  • Connections. Each web replica and each lane thread holds one. Size max_connections for replicas × threads, plus the migrate job.

Redis

  • Production refuses [redis] without tls = true and a ca_certificate. The password is the mounted file redis_password; an ACL user can be named in username.
  • Eviction policy noeviction. An evicted stream or owner key would read as an answer whose process died.
  • One primary endpoint, not cluster mode. No persistence or backup is needed: Redis holds copies in transit, never a record.

Originals

  • [originals] store = "s3", bucket, region, and for a non-AWS store an endpoint (https in production; path-style addressing is used when one is named). Keys are the mounted files originals_access_key_id and originals_secret_access_key; nothing is read from the environment, a profile or an instance role.
  • A bucket that does not answer is never read as "upload it again": conversion fails with "not answering" so Retry works.
  • Turn on versioning or a backup for the bucket - it holds the only copy of each original.

Secrets as files

Why files and not environment variables. An environment variable is visible to every child process, copied into crash reports and printed by diagnostic tools. A file is read when needed, at owner-only permissions, and replacing it rotates the secret. The platform refuses a secret file with any group or other permission bit.
  • Cloud secret mounts are often root-owned or group-readable (Kubernetes secret volumes with fsGroup, for example), which the platform refuses. The dependable pattern is the one secrets-init uses in compose: an init container that reads the secret manager and writes each value into a memory-backed volume owned by uid 10001 at mode 0600, shared read-only with the application containers.
  • ECS does not mount secrets as files; it injects them as variables - so the init container is required there, never the variables.
  • Generate django_secret_key into the secret manager yourself. The entrypoint creates one only when it is missing, and a key on a non-persistent volume would sign sessions that do not survive a restart.
  • Browser-managed credentials are written by web and read by the workers, so managed_secret_directory needs a shared writable volume (EFS, Azure Files, Filestore). Or leave it unset and project every credential from the secret manager - credentials then become operator-only, and an operator's file always wins anyway.

Containers

  • Configuration. The entrypoint's rendered configuration names the compose hosts (postgres, redis). On a cloud, mount your own file at /etc/digitalbrain/production.toml (start from deploy/production.example.toml; leave out the demonstration keys). A mounted file is used for both the owner and the runtime connection, so mount two: the migrate job's names the owner and runtime_user = "digital_brain_runtime"; every other container's names user = "digital_brain_runtime" and password_secret = "database_runtime_password".
  • Roles by DIGITAL_BRAIN_ROLE: one migrate task per release, run to completion before the service update; web with DIGITAL_BRAIN_MIGRATIONS=wait; worker with DIGITAL_BRAIN_LANES set as in docker-compose.scale.yaml.
  • Workers are always on. Lanes poll every one to thirty seconds; a platform that scales to zero or throttles CPU between requests stops them. Run the worker and sandbox as always-allocated services (GKE or a dedicated service elsewhere), not as request-driven ones.
  • The sandbox's limits - read-only root, every capability dropped, no-new-privileges, a process limit and a memory limit - need a platform that offers each. Kubernetes does through the pod security context; check before choosing a serverless runtime for it.
  • Health checks: web at /health/ready with a Host header the platform allows; workers with python manage.py queue_status --check --lanes "$DIGITAL_BRAIN_LANES". A worker's stop grace period must exceed 50 s.
  • Proxy trust. --trusted-proxy '*' is sound only while nothing but the load balancer can reach the web port. Keep web in a private subnet or name the balancer's addresses with DIGITAL_BRAIN_TRUSTED_PROXY.
  • Streams. An answer can stream for up to 180 s, with a heartbeat every 10 s. Allow at least that per request at the balancer and the container platform.
  • Runtime directory. With originals in a bucket, /app/.runtime holds only the rendered configuration and can be per-container. With store = "disk" it holds originals and must be one shared volume for web, worker and sandbox.

Notes per cloud

AWS

ECS Fargate for web; ECS or EKS for worker and sandbox. RDS CA bundle as sslrootcert. ElastiCache with in-transit encryption and an auth token as redis_password. S3 needs no endpoint. RDS Proxy pins sessions that use advisory locks - connecting directly is simpler.

Azure

Container Apps or AKS. Flexible Server with its CA; Azure Cache for Redis on its TLS port. Blob Storage does not speak S3, so originals stay on an Azure Files volume shared by web, worker and sandbox (store = "disk"), or go to an S3-compatible store.

Google Cloud

GKE for all four roles, or Cloud Run for web only. Cloud SQL's server CA with a DNS name on the certificate. Memorystore in server-authentication TLS mode. Cloud Storage through HMAC keys and the XML API endpoint.

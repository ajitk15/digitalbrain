Deployment

Docker Compose: one server, then split

Three compose files stack on one another. docker-compose.yaml alone is a complete deployment on one server. docker-compose.scale.yaml splits it into a migration job, web replicas, a worker, a sandbox and a virus-scan daemon. The observability files add a collector and Prometheus. Nothing has to be prepared on the server first.

Single server

Why it is shaped this way

Named volumes, no bind mounts

A deployment platform deploys from git onto a server nobody prepared. A compose file that assumes host directories fails with a message about a mount, not about what is actually missing.

No published port

expose, never ports. That is the one condition that makes --trusted-proxy '*' sound: only the proxy can reach the listener, so only it can set X-Forwarded-*.

Passwords written twice

The platform reads a secret only at mode 0600 owned by uid 10001; PostgreSQL runs as uid 70 and Redis as 999, and each refuses a file it does not own. So each side gets its own copy of one generated value.

A CA made on first boot

The client connects with sslmode=verify-full, which checks the certificate and the name. Nothing issues certificates for containers, so postgres-certs makes a CA and certificates named postgres and redis, once.

Redis password in a file

Redis reads it from its own configuration file, never its command line, where any process in the container could see it.

A signing key is never replaced

Rotating it signs everyone out and makes authenticator seeds unreadable, so an existing key is kept and only a missing one is created - linked into place, so two containers racing end with one key.

First deploy

  1. Point the domain at the server. An A record for every name you serve; the proxy's certificate authority validates against it.
  2. Create the compose resource. Point the deployment platform at the repository and docker-compose.yaml. Set the domain on the app service with container port 8000, and let the platform write its own proxy labels. Set DIGITAL_BRAIN_HOSTS to every name you serve - an unlisted Host header is refused with 400.
  3. Deploy and wait. The first boot downloads about 1 GB of ClamAV signatures before it listens; the health check's ten-minute start period allows for it. Later deploys reuse the volume.
  4. Read the log. docker compose logs app shows, in order: the rendered configuration, which paths are real volumes (a path that is a plain directory in the image is flagged NOT PERSISTENT), signatures, migrations, the deployment check, the listener.
  5. Make the first administrator. docker compose exec app python manage.py bootstrap_admin - the password is read hidden and never reaches a file, argument or shell history. Everything after that is done in the browser.
  6. Mount what else you use. Bucket keys, Entra client secret, SCIM token - files in platform-secrets, mode 0600, uid 10001. The entrypoint warns at every start while one the configuration needs is missing.

What the entrypoint reads

Non-secret settings come from environment variables and are rendered into /app/.runtime/production.toml. A file mounted at /etc/digitalbrain/production.toml wins and nothing is rendered. Secrets are never variables.

The hosted demonstration

Both compose files build the image's demo target and set DIGITAL_BRAIN_DEMONSTRATION=1. That is production mode with three things allowed: demo reset, Code Factory's local write and tests, and the ServiceOps test workbench. TLS, secure cookies, scanning and the runtime role stay on; the Claude host login is still refused. The container that applies migrations seeds the CarePath folder into demo-workspace once (scripts/init_vps_demo.py) and keeps approved edits over redeploys. Then docker compose exec app python scripts/rebuild_demo.py builds the organizations and applications, prompts twice (hidden) for any new account's password, and reports missing credentials to set on each application's Credentials screen.

For a real production deployment, build the runtime target and leave DIGITAL_BRAIN_DEMONSTRATION unset.

The scaled split

docker compose -f docker-compose.yaml -f docker-compose.scale.yaml up -d
  • Migrations once, before anything serves. migrate runs with restart: "no"; web, worker and sandbox start only after it exits cleanly, so a failed migration stops the deploy before new code serves. The web containers wait rather than apply, which is what lets them be more than one.
  • Replicas are safe because sessions, lockouts and jobs live in the database, and streams, Stop and the API rate limit in Redis. Some deployment platforms name each container themselves and allow one per service - leave DIGITAL_BRAIN_WEB_REPLICAS unset there.
  • Lanes share by claiming rows. Every lane but maintenance claims its own row before acting, so worker and sandbox replicas never run the same step twice. Maintenance is held by one process through a PostgreSQL advisory lock; a second worker stands by. A test holds the two lane lists to the registry with no lane in both.
  • The sandbox is the same image with the three lanes that hand outside content to another program - converters, OCR and the scan; git; the Claude CLI. It writes only /tmp (4 GB tmpfs) and the runtime volume, reads secrets and credentials read-only, drops every Linux capability, cannot gain one, and stops at 512 processes and 6 GB.
  • Stops are honoured between steps. run_worker lets a step in progress finish for up to 50 s; stop_grace_period is 70 s.
  • Health is per service: each worker's check is queue_status --check --lanes for its own lanes only, so one service's trouble does not restart the other.
  • Count connections. Every lane thread holds a database connection while it works; add them against max_connections when raising concurrency or replicas.
Still not sandboxed: chat on Claude starts the CLI on the web container's stream thread, and every container mounts the whole secrets volume, owner's database password included.

Observability overlay

docker compose -f docker-compose.yaml -f docker-compose.observability.yaml up -d
# split deployment:
docker compose -f docker-compose.yaml -f docker-compose.scale.yaml \
  -f docker-compose.observability.yaml -f docker-compose.observability.scale.yaml up -d
  • otel-certs issues the collector a certificate for otel-collector from the same CA, copying only its own key - the collector never mounts the CA's key. Production refuses an http collector.
  • otel-collector (contrib 0.120) receives OTLP/HTTP on 4318, compose network only. Traces go to its log until its traces pipeline names a backend.
  • prometheus (3.2.1) loads deploy/slo-rules.yml, keeps 15 days, and is published on the host's loopback 127.0.0.1:9090 only - reach it over an SSH tunnel or behind the proxy with its own sign-in. Add an Alertmanager to send alerts anywhere.
  • The scale variant points the worker and sandbox at the same collector; each process reports its own service.instance.id, so replicas add up rather than overwrite.

See Observability for what is measured and why.

Day-to-day commands

docker compose exec app python manage.py queue_status --check
docker compose exec app python manage.py slo --check
docker compose exec app python manage.py check --deploy --fail-level WARNING
docker compose exec app python manage.py remove_authenticator <user ID>
docker compose exec app python manage.py move_originals --check

Every docker exec finds the configuration at one path (/app/.runtime/production.toml), because the entrypoint's own environment does not reach a later exec.

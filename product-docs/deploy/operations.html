Deployment

Running it: secrets, TLS, upgrades, backups

What an operator does after the first deploy - and why each step is shaped the way it is. These hold on every deployment shape; the commands use Docker Compose, and the same manage.py commands run in any container.

Every file: mode 0600, readable by uid 10001. The platform refuses a secret with any group or other permission bit. An operator's file always wins over one typed into the Credentials screen, which is why moving a credential into a secret manager needs no change in the product.

Rotating

  • Signing key: put the old value in django_secret_key_previous, the new one in django_secret_key, restart. Sessions and authenticator seeds still open under the previous key. Replaced outright, everyone is signed out and every authenticator app needs a recovery code.
  • Database runtime role: replace database_runtime_password and deploy. apply_migrations states the role's password again on every run, sent as a SCRAM verifier computed in the process, so a server that logs DDL logs no password.
  • Owner, Redis: change them on the server and in the file together (in compose, the copies in database-secret and redis-config too).
  • Provider credentials: an owner replaces them on Settings → Credentials; the value is never shown again. Or replace the file in /run/secrets.

TLS

To the browser

Terminated by the reverse proxy or load balancer, which sets X-Forwarded-Proto. The platform sends HSTS, secure cookies and its CSP; check --deploy fails a start whose cookie or proxy settings are wrong.

Inside

PostgreSQL with verify-full and hostssl only; Redis on its TLS port only; the collector over https. In compose one CA, made on first boot and valid ten years, issues all three certificates, each named for the host the platform dials.

To renew the internal certificates in compose, remove server.key and redis.key from the postgres-certs volume (and otel-collector.key from otel-certs, if you run the overlay) and redeploy. A missing server.key makes the init service issue a new CA with the PostgreSQL certificate, so every certificate must be issued again from it at the same time.

Upgrades and migrations

  • One applier. manage.py apply_migrations holds a session advisory lock on a connection of its own; a second caller says it is waiting, then finds nothing to do. It lifts the 10 s statement timeout for itself (an index on a large table outlasts a request's limit), keeps the lock timeout, and retries a migration only on lock_not_available - each migration is one transaction on PostgreSQL, so a retry starts clean.
  • Expand, then contract. A column is added nullable or with a database default - a Python default is dropped once the column is filled, so the old release's inserts would fail. Removing or renaming waits a release. test_migration_job refuses anything else unless it is named as the second half of such a pair.
  • Every run also creates or corrects the runtime role (undoing any privilege added by hand) and makes the audit table's monthly partitions ahead.
  • Order: build the image → run the migrate job to completion → roll the web replicas → roll worker and sandbox. A stop is honoured between steps, so a conversion or paid call in progress finishes and is recorded.
  • Before restarting the process that runs the factory lane, look for a Code Factory run in flight on Administration → Operations: a restart can stop a run part way through its agent's work.
  • After a release: manage.py scorecard --record on the release commit keeps the measured history in benchmarks/history/.

docker compose exec -T postgres pg_dump -U digital_brain_app -Fc digital_brain > digital_brain.dump

# a volume (repeat per volume; the name carries the compose project prefix)
docker run --rm -v <project>_platform-secrets:/v:ro -v "$PWD":/b alpine tar czf /b/platform-secrets.tgz -C /v .
  • Nothing in the repository backs anything up, and the single-server compose file has one database container, no replica and no point-in-time recovery. A managed PostgreSQL with both is the production answer.
  • Restoring: restore the database, then run apply_migrations. Roles belong to the server, not the database, so a fresh server lacks digital_brain_runtime; the run creates it and grants it every table.
  • Secrets with the data. A database restored without its django_secret_key works, but every authenticator seed in it is sealed under the old key.
  • Rehearse it. A restore nobody has run is a hope.

Retention

Audit events and receipts are kept until a [retention] table says otherwise. audit_days may not be under 2,192 (six years, HIPAA §164.316(b)(2)) and usage_days not under 400; 0 keeps everything. The maintenance lane deletes oldest first in short batches, at most once an interval, and logs counts only. On PostgreSQL, a month's audit partition is dropped only when every row in it is past the window.

Virus signatures

Signatures older than a week are refused, so a scanner that stopped updating fails closed rather than letting files through. In the all-in-one container freshclam runs at start and daily; with clamd the daemon keeps its own and the platform asks it for their date. If every upload fails as "signatures stale" after a first start, restart clamd to load the signatures freshclam replaced.

Disabling and deleting

A platform administrator disables any organization, portfolio, product or application on Administration → Organizations → Structure - reversible, and queued work under it is failed at no cost. Deleting is offered only for something already disabled, needs the exact name typed, and is refused while anything under it is in flight. Audit events and receipts outlive it. On the host: manage.py delete_application <id> --confirm-name <name> --as <admin>.
